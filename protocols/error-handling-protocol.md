# Agent 错误处理协议 · 轻量版

> 错误处理目标：先保护用户意图、Base 链路、QA 闸口和真实代码边界，再决定自动修复、退回补齐、降级处理或请求人类确认。

---

## 1. 错误分类

| 类型 | 判断 | 处理 |
|---|---|---|
| 上下文缺失 | 找不到对应 `RQ / FT / QA / IMP` | 停止实现，退回 PM 补齐 Base 链路 |
| 产品意图不清 | 用户描述有多种解释 | 输出 3-5 个候选方案并推荐 |
| 需求冲突 | 新需求与已确认 RQ / CR 冲突 | 列冲突点，给合并 / 取舍方案 |
| 设计或方案缺失 | 缺少 `PD-*` 或 `TD-*` 就要进入实现 | 停止实现，退回 PM 补产品设计或技术方案 |
| QA 缺失 | `FT-*` 已确认但没有 `QA-*` | 调度 QA Agent，生成 QA 报告并等待人类确认 |
| QA 未通过 | QA 结论为有条件通过 / 不通过，或存在 Critical / High 风险未确认 | 退回 PM 修正对象包；必要时重新 QA |
| 实现偏差 | 代码实现与 Base 或 QA 结论不一致 | 创建 FB 或 CR，做影响分析 |
| 技术阻塞 | 架构、依赖、性能、安全存在风险 | 给 2-4 个技术方案并推荐；高风险需人类确认 |
| 测试失败 | 验证不通过 | 记录 TEST 问题清单，定位后修复，不得声明完成 |
| 破坏性风险 | 删除、迁移、重构、数据变更 | 必须请求人类确认 |
| 文档同步失配 | docs / protocols 与 README、SKILL、智能体提示词或 agents 不一致 | 按同步基准更新说明、索引、链路和禁止事项 |

---

## 2. 处理优先级

```text
保护用户意图
→ 保护 Base 链路
→ 保护 QA 强制闸口
→ 保护现有代码和数据
→ 尝试最小自动修复
→ 给候选方案
→ 请求人类确认
```

---

## 3. 自动处理规则

可以自动处理：

- 明确的格式、命名、引用路径问题。
- 文档、索引、协议中的旧链路同步问题。
- 不改变产品意图的小范围代码错误。
- 测试中暴露的纯实现缺陷。
- Base 对象包内的状态同步和索引更新。
- docs / protocols 与当前 `README.md`、`SKILL.md`、`智能体提示词.md`、`agents/`、`skills/` 的一致性修正。

必须先确认：

- 改变产品目标。
- 改变功能范围。
- 改变核心流程或数据结构。
- QA Agent 输出 Critical / High 风险，或 QA 结论为有条件通过 / 不通过。
- QA 通过后是否允许创建 `IMP-*` 并进入实现。
- 删除、迁移、覆盖已有文件或数据。
- 将一个需求拆分、合并或废弃。

## 4. 标准错误响应

```text
问题类型：<上下文缺失 / 产品意图不清 / 设计或方案缺失 / QA缺失 / QA未通过 / 实现偏差 / 技术阻塞 / 测试失败 / 文档同步失配>
影响对象：<RQ / VR / PD / TD / FT / QA / IMP / CR / TEST / FB / docs / protocols>
当前风险：<一句话说明>
可选处理：<2-4 个方案>
推荐处理：<当前最优方案 + 理由>
是否需要人类确认：是 / 否
下一步：<更新 Base / 调度 QA / 修复代码 / 创建 CR / 补充测试 / 同步文档>
```

---

## 5. QA 相关错误处理

| 场景 | 处理 |
|---|---|
| 缺少 `QA-*` 但用户要求实现 | 停止实现，调度 QA Agent |
| QA 结论为通过且无 Critical / High 风险 | 可进入 IMP，但需记录人类确认 |
| QA 结论为有条件通过 | 修复所有“必须修复”项后，方可进入 IMP |
| QA 结论为不通过 | 退回 PM Agent，修正后重新完整 QA |
| QA 输出 Critical / High 风险 | 必须等待人类明确确认，不得自动进入 IMP |
| Dev 发现实现与 QA 结论冲突 | 停止实现，回传 PM / QA 复核 |

---

## 6. 文档同步错误处理

当发现 docs 或 protocols 与项目最新规则不同步时，按以下顺序处理：

1. 读取同步基准：`README.md`、`SKILL.md`、`智能体提示词.md`、`技能使用场景介绍.md`、`agents/`、`skills/`。
2. 识别失配类型：旧链路、旧目录、旧 Agent 名称、旧 Skill 数量、缺少 QA、仍描述 CLI 或平台适配器。
3. 只修改 docs / protocols 中的说明、索引、协议和维护规则，不写入真实源码。
4. 更新后验证关键关键词和链接：`QA`、`10-QA验证`、`Dev Agent`、`21 个子技能`、`无需 CLI`、`RQ → VR → PD → TD → FT → QA → IMP → TEST → FB → CR`。
5. 若发现同步基准文件之间也互相冲突，先向用户说明冲突范围，再按用户确认处理。

---

## 7. 禁止事项

- 禁止为了继续执行而跳过缺失的 `RQ / FT / QA / IMP`。
- 禁止跳过 `QA-*` 从 `FT-*` 直接创建 `IMP-*`。
- 禁止 QA 未通过或未经人类确认时声明可以实现。
- 禁止把需求偏差当作 BUG 静默修复。
- 禁止在没有影响分析时执行变更。
- 禁止在测试失败时声明完成。
- 禁止把真实源码写入 `Base/`。
- 禁止继续传播不存在的 CLI、平台适配器或安装流程。
- 禁止用复杂错误码系统替代清晰说明。

- [../SKILL.md](../SKILL.md)

- [../agents/orchestrator/SKILL.md](../agents/orchestrator/SKILL.md)
- [../agents/pm-agent/SKILL.md](../agents/pm-agent/SKILL.md)
- [../agents/qa-agent/SKILL.md](../agents/qa-agent/SKILL.md)

- [./communication-protocol.md](./communication-protocol.md)
- [../docs/INTEGRATION-GUIDE.md](../docs/INTEGRATION-GUIDE.md)

同步检查重点：

1. 错误分类是否覆盖 QA 缺失、QA 未通过和文档同步失配。
2. 自动处理规则是否允许 docs / protocols 的同步修正。
3. 必须确认项是否覆盖 QA Critical / High 风险和进入实现授权。
4. 标准错误响应是否包含 `QA`、`docs`、`protocols`。
5. 禁止事项是否覆盖无 QA、QA 未通过、真实源码写入 Base、继续传播旧 CLI 描述。
