# 测试驱动开发与验证 Verification

> 当前项目适配：TDD 流程必须绑定 `FT-*/验收标准.md`，所有测试用例必须与验收标准对应；验证结果必须回写到 `TEST-*` 对象包；未通过验证的实现不得声明完成。

## 1. 测试驱动开发（TDD）

### 1.1 核心原则

**铁律**：没有先写失败的测试，就没有生产代码。

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

**核心原则**：如果你没有看到测试失败，你不知道它是否测试了正确的东西。

### 1.2 适用场景

| 场景 | 是否需要 TDD | 例外条件 |
|---|---|---|
| 新功能开发 | 是 | 一次性原型（需询问用户） |
| Bug 修复 | 是 | 生成的代码（需询问用户） |
| 重构 | 是 | 配置文件（需询问用户） |
| 行为变更 | 是 | - |

### 1.3 红-绿-重构循环

#### RED - 编写失败的测试

编写一个最小的测试，展示应该发生什么。

**测试要求**：
- 一个行为
- 清晰的名称
- 真实代码（除非不可避免，否则不使用 mock）

**示例**：
```typescript
test('失败操作重试3次', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

#### 验证 RED - 看着它失败

**强制性，绝对不要跳过。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试失败（不是错误）
- 失败消息符合预期
- 失败原因是功能缺失（不是拼写错误）

**测试通过？** 你在测试现有行为，修复测试。

**测试错误？** 修复错误，重新运行直到正确失败。

#### GREEN - 最小代码

编写最简单的代码使测试通过。

**示例**：
```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```

不要添加功能、重构其他代码或"改进"超出测试的范围。

#### 验证 GREEN - 看着它通过

**强制性。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（无错误、警告）

#### REFACTOR - 清理

仅在绿色之后：
- 删除重复代码
- 改进命名
- 提取辅助函数

保持测试绿色。不要添加行为。

### 1.4 垂直切片 vs 水平切片

**错误（水平切片）**：
```
RED:   test1, test2, test3, test4, test5
GREEN: impl1, impl2, impl3, impl4, impl5
```

**正确（垂直切片）**：
```
RED→GREEN: test1→impl1
RED→GREEN: test2→impl2
RED→GREEN: test3→impl3
...
```

水平切片会产生糟糕的测试：
- 批量编写的测试测试的是想象的行为，而不是实际行为
- 测试的是事物的形状（数据结构、函数签名），而不是面向用户的行为
- 测试对真实变更不敏感
- 在理解实现之前就提交测试结构

### 1.5 好测试的特点

| 质量 | 好 | 坏 |
|---|---|---|
| **最小** | 一件事。名称中有"and"？拆分。 | `test('验证邮箱、域名和空白')` |
| **清晰** | 名称描述行为 | `test('test1')` |
| **显示意图** | 展示期望的 API | 模糊代码应该做什么 |

### 1.6 红牌警告

| 禁止行为 | 处理方式 |
|---|---|
| 代码先于测试 | 删除代码，用 TDD 重新开始 |
| 测试在实现之后 | 删除代码，用 TDD 重新开始 |
| 测试立即通过 | 修复测试，确保它真正测试了新功能 |
| 无法解释测试为什么失败 | 调查原因，修复测试 |
| 测试"稍后"添加 | 拒绝继续，先写测试 |
| 合理化"就这一次" | 拒绝，坚持 TDD |
| "我已经手动测试了" | 拒绝，坚持 TDD |
| "测试后达到相同目的" | 拒绝，坚持 TDD |
| "这是关于精神而不是仪式" | 拒绝，坚持 TDD |
| "保留作为参考"或"改编现有代码" | 拒绝，坚持 TDD |
| "已经花了X小时，删除是浪费" | 删除，用 TDD 重新开始 |
| "TDD是教条的，我很务实" | 删除，用 TDD 重新开始 |

## 2. 完成前验证

### 2.1 核心原则

**证据驱动**：所有完成声明必须有证据支持。

**多层验证**：
- 单元测试验证
- 集成测试验证
- 端到端测试验证
- 用户验收验证

### 2.2 验证流程

**1. 自检**：开发者自我验证
- 运行单元测试
- 检查代码质量
- 验证功能正确性

**2. 交叉验证**：团队成员交叉检查
- 代码审查
- 功能演示
- 测试用例执行

**3. 最终验证**：正式验收
- 执行完整测试套件
- 验证性能指标
- 确认交付标准

### 2.3 验证清单

标记工作完成前必须检查：

| 检查项 | 说明 |
|---|---|
| 每个新函数/方法都有测试 | 覆盖所有新增代码 |
| 在实现前看到每个测试失败 | 确保测试真正测试了新功能 |
| 每个测试因预期原因失败 | 功能缺失，不是拼写错误 |
| 编写最小代码通过每个测试 | 不要过度实现 |
| 所有测试通过 | 无失败测试 |
| 输出干净（无错误、警告） | 代码质量达标 |
| 测试使用真实代码（仅在不可避免时使用 mock） | 测试真实行为 |
| 覆盖边缘情况和错误 | 确保健壮性 |

## 3. 项目适配约束

### 3.1 Base 链路约束
- TDD 流程必须绑定 `FT-*/验收标准.md`
- 所有测试用例必须与验收标准对应
- 验证结果必须回写到 `TEST-*` 对象包
- 未通过验证的实现不得声明完成

### 3.2 验证报告要求
验证报告必须包含：
- 验证标准（来自 `FT-*/验收标准.md`）
- 验证结果（通过/失败）
- 证据（测试结果、日志等）
- 问题清单（如果有）
- 验收结论（总体状态）
