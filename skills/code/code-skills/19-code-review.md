# 代码审查规范 Code Review Guidelines

> 当前项目适配：代码审查结果必须记录到 `Base/09-测试验收/TEST-*/测试记录.md`，问题必须进入问题清单。

---

## 1. 代码审查流程

### 1.1 审查前准备

1. 确认 PR 标题清晰描述变更内容
2. 确认 PR 描述包含变更原因和影响范围
3. 检查 CI 是否通过
4. 确认测试用例完整

### 1.2 审查步骤

```
检查 PR 描述 → 运行测试 → 阅读代码 → 提出问题 → 讨论 → 批准/拒绝
```

### 1.3 审查标准

| 类别 | 关注点 |
|---|---|
| 功能正确性 | 实现是否符合需求，边界条件是否处理 |
| 代码质量 | 可读性、复杂度、重复代码 |
| 安全性 | 敏感信息、注入风险、权限控制 |
| 性能 | 算法效率、数据库查询、资源使用 |
| 可维护性 | 架构设计、模块化、文档 |
| 测试覆盖 | 单元测试、集成测试、边界测试 |

## 2. 代码审查检查清单

### 2.1 前端审查

- [ ] 组件命名清晰且一致
- [ ] 状态管理合理（useState/useReducer/Zustand）
- [ ] 避免不必要的重渲染（React.memo/useMemo）
- [ ] 样式使用一致（CSS Modules/Tailwind）
- [ ] 错误处理完善（try-catch/错误边界）
- [ ] 可访问性考虑（aria-label/语义化标签）
- [ ] 响应式设计适配
- [ ] 测试用例覆盖

### 2.2 后端审查

- [ ] API 设计符合 RESTful 规范
- [ ] 错误处理和日志记录完善
- [ ] 认证授权正确实现
- [ ] 数据库查询优化（索引使用）
- [ ] 事务处理正确
- [ ] 连接池配置合理
- [ ] 输入验证完善
- [ ] 测试用例覆盖

### 2.3 通用审查

- [ ] 代码风格一致（ESLint/Prettier）
- [ ] 变量和函数命名清晰
- [ ] 注释说明复杂逻辑
- [ ] 没有未使用的代码
- [ ] 没有硬编码的敏感信息
- [ ] 版本号正确更新

## 3. PR 评论规范

### 3.1 评论格式

```
问题类型：[功能错误/代码质量/安全性/性能/其他]
问题描述：[具体问题说明]
建议方案：[修复建议]
```

### 3.2 评论示例

```
问题类型：代码质量
问题描述：这个函数超过 50 行，建议拆分为多个小函数
建议方案：提取 validateInput 和 processData 两个辅助函数
```

### 3.3 审查态度

- **具体**：指出具体问题，不要泛泛而谈
- **建设性**：提供解决方案而非单纯批评
- **尊重**：保持专业和礼貌的语气
- **聚焦**：只关注代码质量，不涉及个人

---

## 4. 审查通过标准

### 4.1 必须满足

- [ ] 所有测试用例通过
- [ ] 没有安全漏洞
- [ ] 实现符合需求
- [ ] CI 构建通过

### 4.2 建议满足

- [ ] 代码复杂度合理
- [ ] 文档完整
- [ ] 代码风格一致
- [ ] 没有未解决的评论

## 5. 代码审查工具

### 5.1 GitHub PR 审查

```powershell
# 查看 PR 变更
gh pr view <PR_NUMBER> --diff

# 评论 PR
gh pr review <PR_NUMBER> --comment "审查意见"

# 批准 PR
gh pr review <PR_NUMBER> --approve
```

### 5.2 代码质量工具

```powershell
# ESLint
npx eslint .

# Prettier
npx prettier --check .

# TypeScript 类型检查
npx tsc --noEmit

# 代码覆盖率
npx jest --coverage
```

---

## 6. 审查后处理

### 6.1 批准合并

1. 确认所有评论已解决
2. 运行最终测试
3. 合并 PR（推荐 squash merge）
4. 删除分支

### 6.2 拒绝修改

1. 明确指出需要修改的问题
2. 等待作者修改后重新审查

## 关键红线

- [ ] 代码审查结果必须记录到 TEST-*/测试记录.md
- [ ] 发现的问题必须进入问题清单
