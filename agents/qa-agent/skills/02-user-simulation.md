# 阶段2 · 用户模拟技能

> 以多角色真实用户视角，沿完整行为路径验证功能逻辑、交互体验和边界场景。

---

## 1. 职责

- 定义 3-5 个典型用户角色（基于 RQ/PD 的目标用户）。
- 为每个角色构建从进入系统到完成核心任务的完整行为路径。
- 在每一步检查：功能是否可用、逻辑是否自洽、体验是否合理。
- 识别断裂点、矛盾点和反人类设计。

---

## 2. 输入

| 来源 | 说明 |
|---|---|
| 阶段1输出 | 产品认知模型（目标用户、关键功能） |
| PD-* | 页面流程、用户路径、交互规则 |
| FT-* | 功能边界、异常场景 |

---

## 3. 执行步骤

### 3.1 定义用户角色

基于 RQ/PD，定义以下典型角色（至少 3 个）：

| 角色类型 | 说明 |
|---|---|
| 核心用户 | 最频繁使用该功能的主要人群 |
| 新用户 / 首次使用者 | 对产品不熟悉、需要引导的用户 |
| 边缘用户 | 特殊场景下的用户（如管理员、审核员、第三方） |
| 对抗性用户 | 可能误操作或恶意使用的用户 |

每个角色需明确：
- 使用动机
- 技术熟练度
- 典型设备 / 环境

### 3.2 构建行为路径

为每个角色设计完整的行为路径，覆盖：

**主流程（Happy Path）**
1. 进入系统 → 找到功能入口
2. 执行核心操作
3. 获得预期结果
4. 离开或继续下一步

**分支流程**
- 中途修改选择
- 使用辅助功能（搜索、筛选、帮助）
- 多步骤操作的中间状态

**异常流程**
- 网络中断 / 加载失败
- 数据为空 / 无权限
- 操作冲突 / 重复提交
- 输入错误 / 边界值

### 3.3 逐点验证 + 路径审计

对每个行为路径的每一步，检查以下维度：

| 维度 | 检查要点 |
|---|---|
| **功能完整性** | 该步骤所需的功能是否已定义？是否存在缺失环节？ |
| **逻辑一致性** | 前后步骤的逻辑是否自洽？状态流转是否合理？ |
| **用户体验** | 操作是否直观？是否需要过多思考或跳转？文案是否清晰？ |
| **错误处理** | 出错时是否有明确提示和恢复路径？ |
| **权限控制** | 不同角色的可见性和可操作性是否正确区分？ |

### 3.4 路径审计（Trajectory Audit）

> 参考：TestQuality Dual-Layer Evaluation。不仅验证最终结果，还要审查每一步决策是否合理——"正确结果 ≠ 正确过程"。

对每个行为路径执行以下审计：

| 审计项 | 说明 |
|---|---|
| **步骤必要性** | 每一步是否是完成目标所必需的？是否存在冗余操作或多余跳转？ |
| **信息充分性** | 用户在每一步是否获得了做出决策所需的信息？还是被迫"盲选"？ |
| **选择合理性** | 系统引导用户做出的选择，是否符合大多数用户的直觉和利益？ |
| **上下文连贯性** | 跨页面/跨步骤的上下文（已填内容、已选选项）是否正确保留？ |
| **决策可逆性** | 关键操作是否提供撤销或二次确认机制？误操作的代价是否合理？ |

如果发现"结果正确但路径不合理"的情况，同样记录为问题：

```
- [角色] <用户角色>
- [步骤] <行为路径中的具体步骤>
- [审计类型] <功能缺失 / 逻辑矛盾 / 体验缺陷 / 异常未处理 / 路径不合理>
- [严重程度] <阻塞 / 重要 / 轻微>
- [描述] <具体问题说明，强调为什么该步骤的决策过程有问题>
- [建议修复] <推荐修改方向>
```

每个问题按以下格式记录：

```
- [角色] <用户角色>
- [步骤] <行为路径中的具体步骤>
- [问题类型] <功能缺失 / 逻辑矛盾 / 体验缺陷 / 异常未处理>
- [严重程度] <阻塞 / 重要 / 轻微>
- [描述] <具体问题说明>
- [建议修复] <推荐修改方向>
```

---

## 4. 输出

写入 `Base/10-QA验证/QA-xxx-功能名称验证/用户模拟记录.md`。

必须包含：
- 定义的用户角色清单
- 每个角色的行为路径（主流程 + 分支 + 异常）
- 发现的问题列表（按严重程度排序）
- 总体体验评估结论
