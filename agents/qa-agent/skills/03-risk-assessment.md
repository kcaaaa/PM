# 阶段3 · 风险评估技能

> 系统性评估技术方案中的技术风险、安全隐患和合规问题，形成结构化风险矩阵。

---

## 1. 职责

- 基于 TD（技术方案）和功能定义，识别潜在的技术实现风险。
- 评估性能瓶颈、可扩展性问题和架构隐患。
- 审查安全策略的充分性。
- 检查合规性和法律风险。
- 输出分级风险矩阵，标注必须处理项。

---

## 2. 输入

| 来源 | 说明 |
|---|---|
| TD-* | 技术方案、接口设计、数据结构、安全策略 |
| FT-* | 功能定义（用于判断技术是否支撑功能） |
| 阶段1输出 | 产品认知模型 |

---

## 3. 风险评估维度

### 3.1 技术可行性风险

| 检查项 | 说明 |
|---|---|
| 技术选型合理性 | 选用的技术栈是否能支撑核心功能？是否存在已知限制？ |
| 依赖风险 | 是否依赖不成熟、维护差或即将废弃的技术/库？ |
| 集成复杂度 | 与现有系统的集成难度是否被低估？接口兼容性如何？ |
| 实现复杂度 | 方案中是否有过于复杂或难以实现的逻辑？ |

### 3.2 性能风险

| 检查项 | 说明 |
|---|---|
| 数据量假设 | 方案是否考虑了大规模数据场景（查询、存储、同步）？ |
| 并发处理 | 高并发场景下的响应能力和降级策略？ |
| 关键路径延迟 | 核心用户路径中是否存在可能导致明显卡顿的环节？ |
| 第三方依赖性能 | 外部 API / 服务的 SLA 是否可靠？超时和重试机制？ |

### 3.3 安全风险（基于 OWASP LLM Top 10 v2025）

以下检查清单参考 OWASP Top 10 for LLM Applications，作为 AI Agent / LLM 相关产品的标准安全审查基线。

| # | OWASP 类别 | 检查项 | 说明 |
|---|---|---|---|
| LL-01 | Prompt Injection（提示注入） | 外部输入是否可能改变系统行为？ | 用户输入、第三方内容、网页抓取数据是否被当作指令执行？是否有隔离层和过滤机制？ |
| LL-02 | Insecure Output Handling（不安全输出处理） | Agent 的输出是否未经校验直接用于下游操作？ | LLM 生成的代码/命令/JSON 是否在执行前经过结构化和安全性验证？ |
| LL-03 | Training Data Poisoning（训练数据投毒） | 模型或知识库的数据来源是否可信？ | RAG 检索源、微调数据集是否有完整性校验和权限控制？ |
| LL-04 | Model Denial of Service（模型拒绝服务） | 是否存在导致资源耗尽的输入模式？ | 超长上下文、递归调用、恶意复杂请求是否会拖垮系统或推高成本？ |
| LL-05 | Supply Chain Vulnerabilities（供应链漏洞） | 使用的第三方库/插件/MCP Server 是否安全？ | 是否有已知 CVE？来源是否可审计？是否存在过度权限？ |
| LL-06 | Sensitive Information Disclosure（敏感信息泄露） | Agent 是否会暴露不应公开的数据？ | API Key、内部路径、用户隐私数据是否在输出中被无意包含？ |
| LL-07 | Insecure Plugin Design（不安全插件设计） | MCP/工具接口是否遵循最小权限原则？ | 每个工具是否有独立鉴权？是否存在"万能 Token"或过度授权？ |
| LL-08 | Excessive Agency（过度自主性） | Agent 的自主决策范围是否合理受限？ | 高风险操作（删除、转账、对外通信）是否需要人类确认或审批流？ |
| LL-09 | Unauthorized Code Execution（未授权代码执行） | Agent 是否能直接执行任意代码/命令？ | 沙箱隔离是否存在？是否有白名单限制可执行的命令和脚本？ |
| LL-10 | AI Hallucination / Misalignment（幻觉与对齐风险） | Agent 是否可能在关键场景给出错误但自信的回答？ | 医疗、金融、法律等高风险领域是否有二次校验或人工兜底机制？ |

### 3.3.1 通用 Web/系统安全补充检查

| 检查项 | 说明 |
|---|---|
| 认证与授权 | 身份验证机制是否健全？权限控制粒度是否合理？ |
| 数据保护 | 敏感数据的加密、脱敏、传输安全？ |
| 输入校验 | 是否存在注入攻击（SQL/XSS/CSRF）风险点？ |
| API 安全 | 接口是否有鉴权、限流、防重放机制？ |
| 会话管理 | Token / Session 的安全策略是否合理？ |

### 3.4 合规与法律风险

| 检查项 | 说明 |
|---|---|
| 数据隐私 | 是否符合适用的隐私法规（如 GDPR/个人信息保护法）？ |
| AI 监管合规 | 是否考虑了 EU AI Act、NIST AI RMF 等 AI 相关法规要求？高风险场景是否有影响评估？ |
| 内容合规 | 用户生成内容的审核机制和法律责任？ |
| 商业合规 | 是否涉及许可证、知识产权或第三方协议问题？ |

### 3.5 可维护性风险

| 检查项 | 说明 |
|---|---|
| 代码复杂度 | 方案是否会导致难以理解和维护的代码结构？ |
| 技术债务 | 是否存在为了短期实现而牺牲长期质量的妥协？ |
| 文档完整性 | 技术方案是否足够清晰，便于后续开发者接手？ |

### 3.6 Systemic Risk（系统性风险）— 多模块交互复合故障

> 参考：Galileo AI / Microsoft Agentic Failure Taxonomy。单个功能正常不代表系统整体安全；Agent 在多服务、多工具链协作中可能产生连锁故障。

| 检查项 | 说明 |
|---|---|
| 级联失败风险 | 一个模块的异常（超时/错误输出）是否会引发其他模块的错误行为？是否有熔断和降级策略？ |
| 数据一致性冲突 | 多个 Agent / 服务同时修改同一资源时，是否可能导致冲突或脏数据？ |
| 权限叠加风险 | 多个工具组合调用后，整体权限是否超出单个工具的预期范围？ |
| 递归/死循环行为 | Agent 是否会陷入无限规划、重试风暴或自我调用的循环？是否有最大步数限制和超时控制？ |
| Shadow AI（影子系统） | 是否存在未记录的工具调用链或"暗线流程"，导致审计盲区？ |

---

## 4. 风险分级标准

每个识别出的风险按以下矩阵评估：

```
严重度 = 影响程度 × 发生概率

影响程度：
- P0（致命）：系统不可用 / 数据丢失 / 法律风险
- P1（高）：核心功能受损 / 明显安全隐患
- P2（中）：非核心功能受影响 / 体验下降
- P3（低）：轻微问题 / 优化空间

发生概率：
- 极高：几乎必然发生
- 高：很可能发生
- 中：可能发生
- 低：不太可能
```

### 风险等级判定

| 组合 | 等级 | 处理要求 |
|---|---|---|
| P0 × 任何概率 | 🔴 必须修复 | 不得进入 IMP，必须先解决 |
| P1 × 极高/高 | 🔴 必须修复 | 同上 |
| P1 × 中/低 | 🟡 建议修复 | 有条件通过，需记录并跟踪 |
| P2/P3 × 任何概率 | 🟢 可选优化 | 可进入 IMP，后续迭代处理 |

| 1 | <描述> | <技术/性能/安全(LL-xx)/合规/维护/Systemic> | P0-P3 | 极高-低 | 🔴🟡🟢 | 必须修复/建议修复/可选优化 | <措施> |
