# 全流程产品 Agent · 操作手册

> **版本**：2.1.0
> **适用对象**：非开发者、产品经理、业务负责人、创业者、AI 编程用户
> **目标**：让 AI 从人类模糊意图出发，生成候选方案、维护 Base 对象包，并按需求链路推进到 QA、实现、测试、反馈和变更。
>
> **默认假设**：使用者不需要懂代码、不需要知道文件应该改哪里，也不需要描述技术实现方式。人类只需说明“想要什么、哪里不对、希望变成什么样”，AI 负责把自然语言转化为 `RQ → VR → PD → TD → FT → QA → IMP → TEST → FB → CR` 对象包、代码修改和验证记录。

---

## 0. 系统简介

本系统是纯 Markdown 文件型 **AI 原生产品协作 Agent / Skill 模板库**。

它不需要安装依赖、不需要 CLI、不需要运行服务。AI 编程工具只要读取项目根目录的 [SKILL.md](../SKILL.md)、[智能体提示词.md](../智能体提示词.md)、[agents/](../agents/)、[skills/](../skills/)、[protocols/](../protocols/) 和 [docs/](./README.md)，即可按规则工作。

核心组成：

- **Orchestrator**：识别真实意图，扫描 Base 状态，生成候选方案并推荐最优路径。
- **PM Agent**：维护 `RQ → VR → PD → TD → FT → QA → IMP → TEST → FB → CR` 链路，确保需求可追溯。
- **QA Agent**：在实现前进行文档解析、用户模拟、风险评估、运营分析和 QA 报告输出。
- **Dev Agent**：QA 通过后，基于 `IMP-*` 实现包执行代码任务并记录验证结果。
- **Domain Agent**：提供数据库、SQL、UI/UX、技术方案、性能等垂直领域支持。

## 1. 核心工作方式

```text
人类输入方向
→ AI 识别意图与当前 Base 状态
→ AI 输出 3-5 个候选方案并推荐最优方案
→ 人类选择 / 修正 / 否定
→ AI 写入或更新 Base 对象包
→ PM 推进 RQ → VR → PD → TD → FT
→ QA Agent 执行实现前验证
→ QA 通过并经人类确认后创建 IMP
→ Dev Agent 执行实现与验证
→ TEST 测试验收
→ FB 反馈 / CR 变更 / 回归测试
```

人类负责判断方向，AI 负责展开方案、评估取舍、维护链路和执行。

## 2. Base 是项目认知数据库

`Base/` 是 AI 的项目基准库。它不是源码目录，也不是单一总文档，而是由独立对象包组成。

```text
Base/
├── 00-项目总览/              # 项目目标、状态看板、阶段进度、决策记录、项目结构基线
├── 01-需求管理/RQ-*/         # 需求说明、AI候选方案、人类确认记录、需求状态
├── 02-验证管理/VR-*.md       # 需求验证记录
├── 03-产品设计/PD-*/         # 页面流程、用户路径、交互规则、设计验收
├── 04-方案设计/TD-*/         # 方案说明、接口设计、数据结构、安全策略、方案评审
├── 05-功能管理/FT-*/         # 功能说明、边界、异常场景、验收标准、关联关系
├── 10-QA验证/QA-*/           # QA报告、用户模拟记录、风险评估矩阵、运营分析、人类确认记录
├── 06-实现管理/IMP-*/        # 实现任务清单、代码文件索引、变更摘要、验证结果
├── 07-反馈管理/FB-*.md       # 用户反馈与实现偏差记录
├── 08-变更管理/CR-*/         # 变更说明、影响分析、AI建议、人类决策、执行记录
└── 09-测试验收/TEST-*/       # 测试用例、测试记录、问题清单、验收结论
```

---

## 3. 对象包规则

| 对象 | 含义 | 规则 |
|---|---|---|
| RQ | 需求 | 每个需求一个文件夹，包含 AI 候选方案与人类确认记录 |
| VR | 验证 | 每个需求验证一份记录，确保需求可执行、无歧义 |
| PD | 产品设计 | 每个功能或需求一个设计包，明确页面流程与交互规则 |
| TD | 技术方案 | 每个功能一个技术方案包，定义接口、数据结构与安全策略 |
| FT | 功能 | 每个功能一个功能包，包含边界、异常场景与验收标准 |
| QA | 实现前验证 | 每个进入实现前的功能一个 QA 包，包含报告、用户模拟、风险评估、运营分析和人类确认 |
| IMP | 实现 | 每个功能实现一个实现包，记录任务清单、代码文件索引、变更摘要和验证结果 |
| TEST | 测试 | 每个功能一个测试验收包，包含用例、记录、问题清单与结论 |
| FB | 反馈 | 每次反馈一份记录，用于偏差分析与后续变更 |
| CR | 变更 | 每次需求或功能变化一个变更包，不直接覆盖原需求 |

总览、README、看板只做导航，不承载具体需求、功能或实现细节。

## 4. Base 与代码工程目录

`Base/` 不存放真实源码。它记录需求、设计、方案、QA、实现任务、测试结果和变更原因；真正可运行的代码、配置、脚本、测试文件放在与 `Base/` 平级的代码工程目录中。

推荐关系：

```text
项目根目录/
├── Base/                 # AI 项目认知库：需求、方案、QA、任务、验收、变更
├── apps/                 # 前端、后台、移动端等应用代码
├── services/             # 后端服务、接口服务、AI 服务等代码
├── packages/             # 公共组件、工具、配置
├── infra/                # Docker、K8s、CI/CD、部署配置
├── scripts/              # 自动化脚本
└── tests/                # 测试代码
```

非开发者不需要判断代码应该放在哪个目录。AI 在进入实现阶段时必须：

1. 读取 `Base/00-项目总览/项目结构基线.md`。
2. 确认存在对应 `RQ-* / FT-* / QA-* / IMP-*`。
3. 根据 `IMP-*` 判断要改哪些工程文件。
4. 自行扫描代码工程目录并定位文件。
5. 修改完成后，把关联文件、验证结果和遗留问题写回 `IMP-*` 与 `TEST-*`。

## 5. 日常使用方式

### 5.1 新项目或新需求

你可以只说方向：

```text
我想做一个面向中小企业的客户跟进工具
```

AI 应先输出：

```text
Base 状态：当前无相近 RQ
意图判断：新需求 / 新产品方向
候选方案：3-5 个
推荐方案：当前最优方案
需要确认：选择 / 修改 / 否定
确认后写入：Base/01-需求管理/RQ-xxx-客户跟进工具/
确认后调度：PM
```

### 5.2 新功能

```text
帮我加一个客户标签功能
```

AI 不应直接编码，而应检查是否已有上级 `RQ-*`，然后生成候选功能方案，并在确认后推进 `RQ → VR → PD → TD → FT`。

### 5.3 QA 验证

```text
这个功能确认了，准备进入实现前先审查一下
```

AI 必须调度 QA Agent，读取相关 `RQ / VR / PD / TD / FT`，生成 `Base/10-QA验证/QA-*`，并输出：

```text
总体结论：通过 / 有条件通过 / 不通过
关键发现摘要：<3-5 条>
必须修复项：<数量>
建议优化项：<数量>
推荐决策：进入 IMP / 修改后重审 / 否决方案
需要人类确认：是
```

QA 未通过或未经人类确认，不得创建 `IMP-*`。

### 5.4 功能实现

```text
开始实现客户标签功能
```

AI 必须确认：

```text
RQ → VR → PD → TD → FT → QA → IMP → TEST 是否完整
```

缺少任一关键对象包时，应先补齐，不得直接写代码。

### 5.5 需求变化

```text
客户标签功能我想改成支持多级标签
```

AI 不应直接覆盖原需求，而应创建或更新：

```text
Base/08-变更管理/CR-xxx-客户标签支持多级/
```

并输出影响分析、处理策略和推荐方案。重大变更或高风险变更必须重新执行 QA。

### 5.6 代码问题或报错

非开发者可以直接描述现象：

```text
点击保存后没有反应。
```

```text
这个页面打开很慢。
```

```text
我不知道哪里出错了，你帮我检查并修复。
```

AI 必须把这类描述转化为可执行的排查链路：

```text
现象理解：<用户描述的问题>
可能原因：<2-4 个方向>
推荐排查顺序：<从低风险到高风险>
关联 Base：RQ / FT / QA / IMP / TEST，如缺失则说明需补齐
下一步：定位对象包、必要时创建 FB / CR、再进入修复与验证
```

用户不需要提供文件路径、函数名、接口名或数据库表名；这些由 AI 在代码工程目录中自行定位。

## 6. 人类如何把控项目

人类不需要管理 AI 的每一步，只需要把控以下闸口：

1. 候选方案是否符合真实意图。
2. 推荐方案是否可接受。
3. 是否允许写入或更新 Base。
4. 是否允许从需求进入设计。
5. 是否接受 QA Agent 的结论。
6. 是否允许 QA 通过后进入实现。
7. 变更是否值得执行。
8. 测试结果是否可验收。

---

## 7. 标准链路

```text
RQ 需求
→ VR 验证
→ PD 产品设计
→ TD 技术方案
→ FT 功能定义
→ QA 实现前验证
→ IMP 实现任务
→ TEST 测试验收
→ FB 反馈
→ CR 变更
→ QA 必要时重审
→ IMP 增量实现
→ TEST 回归测试
```

任何代码实现都必须能追溯到 `RQ / FT / QA / IMP`。

---

## 8. AI 必须遵守的硬规则

1. 新需求、新功能、设计取舍、实现偏好、反馈或变更必须先给 3-5 个候选方案。
2. AI 必须推荐当前最优方案，并说明理由。
3. 无上级 `RQ-*`，不得创建 `FT-*` 或 `IMP-*`。
4. 无已确认的 `AI候选方案.md` 与 `人类确认记录.md`，不得进入产品设计。
5. 无 `PD-*` 与 `TD-*`，不得进入实现。
6. 无 `FT-*/验收标准.md`，不得声明实现完成。
7. `FT-*` 确认后，必须经 QA Agent 验证并生成 `QA-*`。
8. QA 未通过或未经人类确认，不得创建 `IMP-*`。
9. 变更必须创建 `CR-*`，不得直接覆盖原文档。
10. AI 修改代码前必须声明当前对应的 `RQ / FT / QA / IMP`。
11. 总文档只做索引，具体内容必须进入独立对象包。
12. 真实源码不得写入 `Base/`。

## 9. 推荐对话方式

推荐说法：

```text
我想做一个 XX，但还没想清楚，你先给我几个方案并推荐一个。
```

```text
选方案 B，但保留方案 C 的数据统计能力。
```

```text
这个功能定义确认了，请先做 QA 验证。
```

```text
QA 通过，按当前 IMP 开始实现。
```

```text
这个实现不符合我的想法，请创建反馈和变更并分析影响。
```

不推荐说法：

```text
直接帮我写代码。
```

除非对应 `RQ / PD / TD / FT / QA / IMP` 已经完整。
